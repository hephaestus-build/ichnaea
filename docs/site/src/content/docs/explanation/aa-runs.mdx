In an A/A run, the base and the candidate are the same configuration.
Nothing changed, so the right answer is "no decrease".
A REGRESSION from an A/A run is a false alarm.

## What an A/A run checks

The statistics are validated in Ichnaea's own studies. Your pipeline is not.
An A/A run checks the parts that Ichnaea cannot see:

- your cases, and how your system answers them
- how your runner records outputs, retries and failures
- how your measures score the answers
- whether the two arms really ran under the same conditions

If any of these differs between the arms, an A/A run can show a decrease that is not real.

## What it does not check

- **The method's error rate.** One A/A run is one draw. A clean run does not prove that false alarms are rare. The validation studies measure that.
- **Your next change.** An A/A run says nothing about a candidate that does change.

## When to run one

Before you make a gate required in CI, run two A/A runs. This is advice: Ichnaea does not check it.
Run them again when you change the runner, the endpoint or how you score.

At one trial per case, clean A/A runs are a condition of the method itself.
With one trial, a shock between the two arms looks like an effect.
So the plan must cite at least two separate A/A decisions, each at one trial per case on the same suite, model and schedule.
Each must give no REGRESSION and pass Ichnaea's eight checks of its records. Otherwise the result is not validated.
An A/A REGRESSION blocks one trial per case for that suite, model and schedule.
The block stays until its cause is found and two later A/A decisions are clean.
